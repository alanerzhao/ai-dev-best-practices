# 评估（Evals）

改提示词、改模型、改工具，都要先跑评估再上线。没有评估结果的 PR 不合并。

单条用例用 [`case-template.md`](case-template.md)。

## 三类集合

| 集合 | 用途 | 规模 | 谁维护 |
| --- | --- | --- | --- |
| **Golden** | 代表正确行为的固定集。发版门禁。 | 每个场景 20–50 条起 | 产品 + 工程 |
| **Regression** | 曾经坏过的案例 + 高风险边缘。每次改动必跑。 | 随失败案增长，不删 | 工程 |
| **Failure** | 当前已知失败。用于排期和防回归。 | 每条 P0/P1 一个文件 | 拥有者 |

目录建议：`evals/{prompt-id}/{golden,regression,failure}/{case-id}.md`

## 怎么跑

1. **冻结输入**：用例里的 input 不要临时改。要改就开新用例。
2. **对照 expected**：能精确匹配的字段精确匹配（枚举、ID、JSON key）；自由文本用打分规则或 LLM-as-judge，规则写在用例里。
3. **一次跑全集**，不要只挑自己改过的那几条。
4. **记录**：提示词版本、模型 ID、日期、通过数 / 失败 ID。贴到 PR。
5. **失败入集**：线上或回归新踩的案，3 个工作日内补成用例，挂 owner。

## 通过门槛（Pass / Fail bar）

每个场景自定义数字，不要默认 100%。建议起点：

| 集合 | 默认门槛 | 说明 |
| --- | --- | --- |
| Golden | ≥ 90% 通过，且 **0** 条 P0 失败 | P0 = 越权、编造事实、错误删除、对外乱发 |
| Regression | **100%** | 曾经坏过的不允许回滑 |
| Failure | 不设通过率 | 用来跟踪已知缺陷；修好后搬进 regression |

发布门禁：

- Golden 不达标 → 不能上产
- Regression 任一条失败 → 不能上产
- 新增 P0 失败且没有缓解措施 → 不能上产

MAJOR 提示词 / 换模型：必须出新旧对比表（同一集合两次跑分）。新版不得低于旧版超过公差 2 个百分点，除非产品签字接受。

## 失败案怎么处理

1. 用例标 `fail`，填实际输出 vs expected 的差异。
2. 定级：P0 当天定 owner；P1 进近一个迭代；P2 进负债。
3. 修好后：再跑通过 → 搬到 regression → 从 failure 移除。
4. 不要删 golden 来「让通过率好看」。用例过时才能废弃，废弃要写原因。

## 谁对结果负责

- 工程：跑评估、贴结果、维护回归集。
- 产品：定门槛、定 P0、抽查自由文本打分。
- 拥有者字段见每条用例，不得空着。
